RSA en Java, del papel al código que sí compila

Hasta acá vimos la teoría, cómo funciona RSA, por qué es seguro, y qué puede salir mal si se implementa mal. En esta entrada eso se vuelve código real, organizado siguiendo las fases del ciclo de vida del desarrollo de software (SDLC).

Fase de diseño, modelar la amenaza antes de escribir código

Antes de programar nada, un equipo responsable se pregunta qué puede salir mal. OWASP propone un proceso de modelado de amenazas de cuatro pasos (Conklin, s. f.) que aplico aquí a un caso concreto, una función que cifra documentos confidenciales (por ejemplo, un reporte PQRS) antes de enviarlos a un tercero.

  1. Delimitar el trabajo: el activo a proteger es el contenido del documento y, sobre todo, la clave privada que lo descifra.
  2. Determinar las amenazas: con STRIDE, divulgación de información si la clave privada queda expuesta, y suplantación si alguien entrega una clave pública falsa.
  3. Determinar contramedidas: padding seguro y gestión de la clave privada fuera del código fuente.
  4. Evaluar el trabajo: verificar que exista evidencia de los tres pasos anteriores.

Fase de construcción, el código real

Usé KeyPairGenerator para generar el par de claves, y Cipher con el modo OAEP en vez del PKCS1 clásico. El padding OAEP es justamente la contramedida frente al ataque de texto plano escogido que vimos en la Entrada 2.

import javax.crypto.Cipher;
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.PrivateKey;
import java.security.PublicKey;
import java.util.Base64;

public class RsaDemo {

    public static void main(String[] args) throws Exception {
        // 1. Generación segura del par de claves (2048 bits: mínimo recomendado)
        KeyPairGenerator keyGen = KeyPairGenerator.getInstance("RSA");
        keyGen.initialize(2048);
        KeyPair keyPair = keyGen.generateKeyPair();

        PublicKey publicKey = keyPair.getPublic();
        PrivateKey privateKey = keyPair.getPrivate();

        // 2. Cifrado con padding OAEP (NUNCA usar RSA/ECB/PKCS1Padding en produccion)
        String mensajeOriginal = "Reporte PQRS confidencial - Direccion de Areas Protegidas";
        Cipher cifrador = Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding");
        cifrador.init(Cipher.ENCRYPT_MODE, publicKey);
        byte[] textoCifrado = cifrador.doFinal(mensajeOriginal.getBytes("UTF-8"));

        // 3. Descifrado con la clave privada
        Cipher descifrador = Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding");
        descifrador.init(Cipher.DECRYPT_MODE, privateKey);
        byte[] textoDescifrado = descifrador.doFinal(textoCifrado);

        String mensajeRecuperado = new String(textoDescifrado, "UTF-8");
        System.out.println("Mensaje descifrado: " + mensajeRecuperado);
        System.out.println("Coincide: " + mensajeOriginal.equals(mensajeRecuperado));
    }
}

Corre el mismo algoritmo, aquí mismo, en tu navegador

Esto no es una simulación, es RSA-OAEP real ejecutado con la Web Crypto API nativa del navegador, el mismo algoritmo del código Java de arriba (2048 bits, OAEP con SHA-256).

Presiona el botón. La generación de una clave de 2048 bits puede tardar uno o dos segundos.

Dos decisiones de diseño no son casualidad, y conectan directo con la Entrada 2. 2.048 bits, no menos, es el tamaño mínimo que tanto Hernández (2016) como Maillo (2017) señalan como aceptable hoy. Padding OAEP, no PKCS1 básico, sin un padding robusto RSA es determinístico (el mismo mensaje siempre da el mismo criptograma), lo que facilita ataques de texto plano escogido.

Fase de despliegue, lo que el código nunca debe hacer

El ejemplo genera las claves en memoria solo con fines demostrativos. En una aplicación real, la clave privada nunca debe quedar escrita en el código fuente, subirse al control de versiones, o aparecer en logs. En su lugar, como vimos en la Entrada 1, vive en un keystore o en un gestor de secretos (Vault, AWS Secrets Manager) al que el servicio accede en tiempo de ejecución.
